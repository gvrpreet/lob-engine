# Experiment: rdtscp timer + log-bucket latency histogram            Date: 2026-09-27      Commit: baseline ca59097 + working tree
**Hypothesis:** Per-event latency currently costs two `steady_clock::now()` calls (~20-30 ns each via vDSO) plus a `push_back` into a 4 MB `uint32_t` vector per 1M events. (1) An `rdtscp`+`lfence` timer should cut the per-read cost to roughly 10-15 ns, which lowers the measurement floor that dominates the ~50 ns p50. (2) An HDR-style histogram (exact below 64 ns, <= 1/32 relative bucket width above) keeps its ~15 KB of counters cache-resident instead of streaming 4 MB, so latency-enabled runs should disturb the book's cache footprint less. Percentiles should agree with the exact `nth_element` values within one bucket.
**Change:** Added `replay/latency_histogram.hpp` (1,920 log-linear buckets, same rank definition as the old `nth_element` percentile, reports the bucket's highest equivalent value capped at the recorded max). It replaces `ReplayStats::latency_ns`. Added `replay/timer.hpp` with `SteadyTimer` and `TscTimer` (`rdtscp` + `lfence`), 5×10 ms median calibration against `steady_clock`, a CPUID invariant-TSC check, and `timer_overhead_ns()` (median empty start/stop interval). Selection is via `ReplayConfig::latency_timer`, which defaults to `SteadyClock` so earlier log rows stay comparable. `replay_cli --tsc` selects rdtscp. `bench_match` now prints both timers with their overhead and checks that the latency-run checksums match. Tests pin bucket math, percentile agreement with exact order statistics, TSC-vs-steady agreement, and replay equivalence with either timer.
**Method:** `data/events_1M.bin` (seed 42), `taskset -c 2 replay_cli ... --no-strategy`, seven alternating runs of four variants: the old commit `ca59097` (vector + steady_clock), histogram + steady_clock, histogram + rdtscp, and unmeasured. Release preset (`RelWithDebInfo`, `LOB_NATIVE=ON`), GCC 13.3, Ryzen 7 7840HS, WSL2 kernel `6.18.33.2-microsoft-standard-WSL2`, clocksource `tsc`. Cachegrind used separate non-native Release builds of both commits.
**Results:** All runs gave checksum `ba7911b3a1dd1d8a`.

Timer overhead probe (median empty interval): steady_clock 20 ns, rdtscp 19 ns. TSC 0.2600 ns/tick (3.846 GHz), CPUID invariant=yes.
**Explanation:** (2) Held in the cache model: the histogram removes the measurement's footprint (LLd misses/event with latency on equal the unmeasured 4.01, vs 4.96 with the vector) and saves ~27 instructions/event. Wall-clock throughput did not improve (ranges overlap). The vector's sequential stores are prefetch/write-combining friendly, so simulated misses cost little real time. The dominant cost is the timer itself: two ~20 ns reads take the run from ~33M to ~14.5M ev/s. (1) Was refuted on this host. WSL2's clocksource is already the TSC, so vDSO `steady_clock` is an `rdtsc` plus scaling and costs the same as `rdtscp`. The `lfence` then blocks overlap with the next event, which lowers throughput by ~10% without lowering the floor. The p50 of 39 ns includes the ~20 ns timer overhead.
**Surprises / next questions:** The first implementation instantiated the replay loop once per timer. That exhausted GCC's inlining budget: `std::map::operator[]`, `FlatOrderIndex::{insert,erase,contains}` and `PriceLevel::unlink` went out of line even in the unmeasured path (+27 instructions/event, found with `cg_annotate`). The fix was one instantiation per book with a predictable runtime timer switch. Lesson: measurement plumbing can change the code it measures, so check unmeasured I refs after touching the replay loop. Next: on native Linux, compare against a non-TSC clocksource, and time batches of N events (not single events) to get sub-timer-overhead resolution. Keep steady_clock as the default and rdtscp opt-in until a host shows a benefit.
