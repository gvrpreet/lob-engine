# Experiment: Flat order-ID index            Date: 2026-09-26      Commit: pending
**Hypothesis:** Replacing `std::unordered_map<OrderId, Handle>` with a flat, power-of-two, linear-probing table will reduce lookup instructions and data references by avoiding node allocation and pointer chasing. Backward-shift deletion should preserve lookup correctness without tombstones.
**Change:** Added `FlatOrderIndex`, sized to a power of two strictly larger than the pool capacity. It provides `contains`, `find`, `insert`, and backward-shift `erase`. Only the order-ID index changed; price levels remain `std::map`, and the 32B AoS pool remains the default.
**Method:** Compared baseline commit `6e1ea00` with the working-tree implementation. Release measurements used the `RelWithDebInfo` preset with `LOB_NATIVE=ON`, GCC 13.3, 1M generated synthetic events (seed 42), CPU affinity core 2, and seven measured runs per invocation. Three invocations per implementation produced identical checksums. Hardware: AMD Ryzen 7 7840HS under Ubuntu 24.04 / WSL2 kernel `6.18.33.2-microsoft-standard-WSL2`; governor was not exposed. Cachegrind used matching non-native Release builds with cache simulation enabled and a 100k-event harness run (41 replay passes including warm-ups and latency pass).
**Results:** Replay checksum remained `ba7911b3a1dd1d8a`. Across three seven-run invocations, per-invocation 32B medians were 12.50-13.62M events/s for the unordered-map baseline and 22.49-24.80M events/s for the flat index; run-to-run spread remains material. The middle observed medians were 13.36M and 23.16M events/s, respectively. Timer-instrumented p50/p99/p99.9 values also trended lower, but are noisy and include timer overhead. `perf` hardware counters are unavailable in this WSL2 environment.
**Explanation:** Cachegrind simulated instruction references fell from about 773 to 490 per processed event, and data references fell from about 426 to 202 per event. Simulated D1 misses rose slightly (about 20.1 to 20.6 per event), as did simulated last-level data misses (about 17.6 to 19.4 per event). Thus the throughput improvement is not explained by fewer simulated cache misses; the fewer references/instructions are consistent with less node/hash-table overhead, but hardware counter evidence is needed to explain the full timing delta. Treat the measured throughput gain as promising, not conclusive.
**Surprises / next questions:** Why do simulated data misses rise despite fewer data references? Recheck with hardware branch/cache counters on a native Linux host and with broader ID distributions and higher live-order counts. Keep the flat index as the experimental implementation for now; do not claim a cache-miss reduction.
